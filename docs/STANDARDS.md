# 공통 개발 기준

프롬프트는 검사할 수 없습니다.

프로젝트마다 복사한 긴 문단은 인용할 수는 있어도 정산되지 않습니다. 그렇게 모인 문서는 아무것도 재지 않으면서 포괄적으로 보입니다. GoalForge 의 공통 개발 기준은 데이터입니다 — 기준 하나가 **무엇으로 정산되는지**와 **그러려면 어떤 근거가 필요한지**를 함께 싣기 때문에, "이 항목은 충족되었다" 는 프로그램이 거절할 수 있는 주장이 됩니다.

---

## 기준 하나의 모양

```go
{ID: "UX-004", Revision: 1, Title: "새로고침과 직접 경로 접근 유지",
 Category: "usability", Severity: SeverityRequired,
 AppliesWhen: map[string]string{"frontend": "react"},
 Checks: []Check{
   {Type: "browser_journey", Assertion: "중첩 경로 직접 접근 시 같은 화면을 표시한다"},
   {Type: "browser_journey", Assertion: "필터를 적용한 뒤 새로고침해도 필터가 유지된다"},
 },
 EvidenceRequired: []string{"commit_sha", "route", "browser_test_result", "screenshot"},
 ChangeScopeHint:  []string{"web/src/routes/**", "internal/http/**"}}
```

| 필드 | 없으면 |
| --- | --- |
| `Checks` | 문서 속 문장입니다. 사람들에게 인용될 뿐 끝나지 않습니다 |
| `EvidenceRequired` | 의견으로 정산됩니다 |
| `AppliesWhen` | AI 가 없는 프로젝트가 스트리밍 기준을 어기고 있는 것으로 보고됩니다 |
| `ChangeScopeHint` | 생성된 과제가 저장소 전체를 범위로 들고 옵니다 |

**필수 기준은 실행해야만 얻는 근거를 요구해야 합니다.** 커밋 SHA 와 경로는 대상을 가리킬 뿐 동작을 말하지 않습니다. 읽어서 정산되는 필수 기준은 저장 버튼이 stub 에 연결된 화면을 "저장 가능" 으로 통과시킵니다.

실행 근거로 인정되는 종류: `browser_test_result`, `integration_test_result`, `security_test_result`, `build_log`, `release_asset`, `screenshot`.

권장(`recommended`) 기준은 읽어서 정산해도 됩니다. 발견 사항이지 게이트가 아니기 때문입니다.

## 프로젝트 프로필

프로젝트는 팩 버전을 **고정합니다**.

```go
Profile{ProjectID: "PRJ-1", PackRef: "go-react-offline-service@0.1",
        Attributes: map[string]string{"frontend": "react", "network": "offline"}}
```

`Attributes` 는 기준의 `AppliesWhen` 과 맞춰집니다. 맞지 않는 기준은 이 프로젝트의 결함이 아니므로 현황에 나오지 않습니다.

새 팩 버전은 **차이를 제안할 뿐 다시 판정하지 않습니다.**

```go
diff := standards.DiffPacks(v01, v02)
// diff.Added   — 새로 생긴 기준
// diff.Removed — 없어진 기준
// diff.Revised — 개정되어 기존 평가를 다시 돌려야 하는 기준
```

저장소는 그대로인데 어제 끝낸 일이 오늘 결함이 되면 안 됩니다.

팩 체크섬도 함께 고정됩니다. 제자리에서 수정된 팩은 버전이 그대로이므로, 체크섬이 없으면 프로필은 여전히 `0.1` 이라고 말하는데 프로젝트는 동의한 적 없는 기준으로 판정됩니다.

## 예외

```go
Exception{StandardID: "NET-002", Reason: "자산 반입이 아직 끝나지 않았습니다",
          Decider: "hkjang", ReviewWhen: "반입 완료 시"}
```

| 요구 | 이유 |
| --- | --- |
| 사유 | — |
| 결정자 | 아무도 소유하지 않은 예외는 누락이 결정의 옷을 입은 것입니다 |
| 재검토 날짜 또는 조건 (**필수 기준만**) | 없으면 정당화했던 사정보다 예외가 오래 살아남고 아무도 눈치채지 못합니다 |

기한이 지난 예외는 **더 이상 면제하지 않습니다.** 그렇지 않으면 6주짜리 유예가 영구가 됩니다.

팩에 없는 기준에 대한 예외는 거절됩니다. 아무것도 면제하지 못하면서 오타를 결정처럼 보이게 합니다.

`AppliesWhen` 에 맞지 않는 것과 예외로 뺀 것은 **구분해서** 보고합니다. 앞은 프로젝트에 대한 사실이고 뒤는 누군가 내린 결정입니다.

## 판정

다섯 가지 결과를 씁니다. 각각이 요구하는 행동이 다르기 때문입니다.

| 결과 | 뜻 | 다음 행동 |
| --- | --- | --- |
| `MET` | 필요한 종류의 근거가 모두 관측되었다 | 없음 |
| `UNMET` | 충족되지 않았다 | 작업 |
| `PARTIAL` | 일부만 | 더 작은 작업 |
| `UNKNOWN` | 판단할 근거가 없다 | 조사 |
| `NOT_APPLICABLE` | 적용하지 않기로 결정했다 | 없음 (예외 기록 필요) |

**판정은 위로 올라가는 실패만 막습니다.**

```
근거가 아예 없음                → UNKNOWN  "browser_test_result 근거가 없습니다"
근거 항목은 있는데 내용이 빔    → UNKNOWN  표시만 된 체크박스는 근거가 아닙니다
근거가 실행이 아니라 추정       → UNKNOWN  "browser_test_result 근거가 추정입니다"
모든 필수 종류가 관측됨          → MET
```

`UNMET` 은 불필요할 수도 있는 작업을 만들고 `MET` 은 아무도 확인하지 않은 것을 내보냅니다. 비싼 쪽은 후자라 그 방향만 막습니다.

`NOT_APPLICABLE` 은 **기록된 예외가 있을 때만** 가능합니다. 관측기가 스스로 제외할 수 있으면, 프로젝트를 재는 것이 무엇으로 재일지를 정하게 됩니다.

측정하지 않은 기준은 빠뜨리지 않고 `UNKNOWN` 으로 보고합니다. 측정한 것만 보여 주는 목록은 아무도 다 걷지 않은 카탈로그를 완전한 것으로 읽히게 합니다.

기준 개정판이 올라간 뒤의 옛 평가는 `stale` 로 표시합니다. 그 평가는 잰 것에 대해서는 여전히 유효하고, 지금 묻는 질문에 답하지 않을 뿐입니다.

## 중복 접수 방지

같은 결함은 두 번 접수되지 않습니다. 키는 **제목이 아닙니다.**

```
dedup_key = sha256(프로젝트 + 기준 ID + 결함 종류 + 대상 범위)
```

새 아이디어를 요구받은 생성기는 같은 공백에 대해 매 사이클 새 문장을 써냅니다. 그걸 다 받는 보드는 진짜 백로그를 바꿔 쓴 말들 아래 묻습니다. 제목 유사도는 이 키가 보지 못하는 경우를 위한 보조 수단이지 주 수단이 아닙니다.

같은 기준이라도 결함 종류나 대상 범위가 다르면 다른 발견입니다.

## 저장소를 읽어 평가하기

```sh
goalforge standards profile --attributes "frontend=react,network=offline"
goalforge standards assess              # 읽기만 합니다
goalforge standards assess --supply     # 미충족 기준을 작업으로 공급합니다
goalforge standards status
goalforge standards except --standard NET-002 --reason "..." --decider hkjang --review-when "..."
```

관측은 **커밋에 고정해서** 합니다. 작업 트리 읽기는 재현되지 않고 아무도 커밋하지 않은 파일까지 포함합니다 — 한 기계에만 존재하는 변경으로 평가가 통과할 수 있습니다.

```
$ goalforge standards assess --supply

공급: WORK-…767397819, WORK-…770377201, WORK-…773334294
자동 검사 없음 24건: CFG-002, CFG-003, CFG-004, NET-001, …

$ goalforge standards status
go-react-offline-service@0.1 — 적용 28건
충족 0 · 미충족 3 · 일부 0 · 미확인 25 · 적용 제외 0
```

### 관측기가 할 수 있는 일과 할 수 없는 일

**부재는 증명할 수 있습니다.** 번들 자산 안의 CDN 주소, 계약이 허용한 네 개를 넘는 환경변수, 실행 단계에서 프런트엔드를 빌드하는 Dockerfile — 소스에 보입니다.

**동작은 증명할 수 없습니다.** 라우터에 경로가 있다는 것은 그 화면이 필터를 복원하는지에 대해 아무 말도 하지 않고, 테스트 파일이 있다는 것은 그 테스트가 통과하는지에 대해 아무 말도 하지 않습니다.

그래서 관측기는 부재가 보이면 `UNMET`, 그 밖에는 **무엇이 정산할지를 적은 `UNKNOWN`** 을 냅니다. 실행이 필요한 것에 `MET` 을 내지 않습니다 — 정적 탐지기가 `MET` 이나 `NOT_APPLICABLE` 을 반환하면 그 탐지기에서 실패합니다.

정적 읽기는 **실행 근거를 만들 수 없습니다.** 파일 읽기를 `browser_test_result` 라고 이름 붙이는 탐지기는 다른 모든 검사를 지나갑니다 — 판정기는 근거의 *종류*만 보지 누가 만들었는지 보지 않기 때문입니다.

### 현재 자동 검사가 있는 기준

| 기준 | 증명하는 부재 |
| --- | --- |
| CORE-001 | go.mod 또는 react 의존성 없음 |
| CFG-001 | 계약의 네 변수를 넘는 런타임 환경변수 (테스트 파일 제외) |
| NET-002 | 프런트엔드 자산의 CDN·외부 폰트 참조 |
| REL-001 | Dockerfile 없음, 또는 **마지막 FROM 이후** 단계에서 프런트엔드 빌드 |

빌드 단계에서 Node 를 설치하는 것은 올바른 방식입니다. 그것을 결함으로 보고하면 해결책을 결함이라고 말하는 셈이라, 마지막 `FROM` 이후만 봅니다.

나머지는 `자동 검사 없음` 으로 **빠뜨리지 않고 말합니다.** "봤는데 문제 없음" 과 "아무도 안 봤음" 은 다르고, 뒤를 생략한 보고서는 아무도 다 걷지 않은 카탈로그를 완전한 것으로 읽히게 합니다.

### 공급

`--supply` 를 붙였을 때만 작업이 만들어집니다. 저장소를 읽는 것이 누군가의 보드에 일을 올려서는 안 됩니다.

- **`UNKNOWN` 은 접수하지 않습니다.** 조사는 결함이 아니고, "가서 봐라" 를 수정처럼 보드에 올리면 아무도 잘못됐다고 확인하지 않은 것들이 쌓입니다.
- **순위를 매긴 뒤에 상한을 적용합니다.** 먼저 도는 탐지기가 무엇을 찾았든 한 회차 예산을 다 쓰는 일이 없습니다. 넘친 것은 버리지 않고 보류합니다.
- **미완료 공급 작업이 10건 쌓이면 공급을 멈춥니다.** 아무도 처리하지 않는 보드에 필요한 것은 더 많은 발견이 아니라 있는 것을 닫는 일입니다.
- **같은 결함은 다시 접수되지 않습니다.** 두 번째 평가는 `이미 접수됨: NET-002 → WORK-…` 이라고 말합니다.

카드는 관측한 것과 기준의 의도를 이고 갑니다. 인수 조건은 **기준 자신의 검사**라서, 일을 접수하는 쪽과 판정하는 쪽이 같은 문장을 읽습니다.

```
NET-002: 프런트엔드 자산 로컬 제공          범위 web/**   우선순위 90

런타임에 외부 자산을 불러옵니다: fonts.googleapis.com (web/index.html)

관측: web/index.html 가 fonts.googleapis.com 를 참조합니다

기준: JS·CSS·폰트·아이콘·도움말을 로컬에서 제공하고 런타임 CDN·외부 텔레메트리를 없앤다

--- 인수 ---
- [browser_journey] 브라우저 요청에 미허용 외부 도메인이 없다
- [static] 런타임 CDN·외부 텔레메트리 참조가 없다
근거: commit_sha, browser_test_result
```

## 이유가 있을 때만 평가하기

`assess` 는 시키는 대로 합니다. `pass` 는 **판단합니다.**

```sh
goalforge standards pass [--interval 24h] [--backlog-floor 3] [--daily-budget 4] [--supply-limit 3]
```

```
$ goalforge standards pass
평가했습니다 (SCHEDULED): 이 프로젝트를 아직 한 번도 평가하지 않았습니다
공급: WORK-…439248023, WORK-…442722545, WORK-…446621359

$ goalforge standards pass
평가하지 않았습니다: 마지막 평가 이후 6ff00562669d 에서 바뀐 것이 없습니다

$ git commit -m "change" && goalforge standards pass
평가했습니다 (COMMIT_CHANGED): 기본 브랜치가 6ff00562669d 에서 abfb07b3074c 로 바뀌었습니다
```

### 평가하는 이유

| 계기 | 언제 |
| --- | --- |
| `SCHEDULED` | 한 번도 평가한 적이 없거나, 마지막 평가로부터 주기가 지났을 때 |
| `COMMIT_CHANGED` | 기본 브랜치가 움직였을 때 |
| `BACKLOG_LOW` | 실행 가능한 대기 작업이 하한보다 적을 때 |

**같은 커밋을 다시 읽으면 같은 답이 나오고 예산만 씁니다.** 그래서 코드가 그대로면 코드와 무관한 이유만이 다시 볼 근거가 됩니다. 반대로 커밋이 그대로라도 주기가 지나면 봅니다 — 팩 개정이나 예외 만료로 저장소가 커밋 없이 기준에서 멀어질 수 있어서, "바뀐 것 없음" 은 "볼 것 없음" 과 다릅니다.

**대기 작업 수는 실제로 집을 수 있는 것만 셉니다.** 서로를 기다리는 마흔 건은 실행기 입장에서 빈 보드이고, 행 수를 세는 공급기는 프로젝트가 멎은 것을 영영 모릅니다.

### 발견 예산

```
$ goalforge standards pass --daily-budget 2
발견 예산을 다 썼습니다: discovery budget spent for today: 오늘 2회
```

구현 예산과 **별개**입니다. 일을 찾는 것과 하는 것은 같은 토큰을 놓고 다투고, 구현 예산에서 빌려올 수 있는 발견 루프는 하루 종일 무엇을 할지 정하다가 아무것도 하지 않습니다.

실패한 시도도 예산을 씁니다. 매번 깨지는 평가야말로 예산이 막으려는 루프입니다.

**예산 소진과 할 일 없음은 밖에서 보면 같아 보이고 대응은 전혀 다릅니다.** 그래서 따로 말합니다.

### 같은 이벤트는 한 번만

평가는 **프로젝트 + 커밋 + 계기** 를 키로 씁니다. 같은 전달이 재시도되거나 두 워커가 같은 커밋을 봐도 하나로 수렴합니다.

- 이미 **완료된** 평가는 반복하지 않습니다. 반복하면 그 발견들을 두 번 접수합니다.
- **실패한** 평가는 다시 시도합니다. 하룻밤 사고로 프로젝트가 평가되지 않은 채 남으면 안 됩니다.
- **진행 중인** 평가는 건드리지 않습니다. 단, 살아 있는 평가라고 보기 어려울 만큼 오래 running 이면 버려진 것으로 보고 이어갑니다 — **모든 재시도를 영원히 막는 멱등 키는 그 키가 막으려던 바로 그 고장입니다.**
- 도중에 죽은 평가는 `FAILED` 로 닫습니다. 그래야 다음 시도가 버려짐 판정 시간을 기다리지 않고 바로 재시도합니다.

실패한 평가는 **마지막으로 본 시점이 아닙니다.** 아무것도 관측하지 못했으니까요.

## 실행해서 판정하기

정적 읽기는 `MET` 을 낼 수 없습니다. **게이트를 돌리는 것만이 기준을 위로 올립니다.**

```sh
goalforge standards gate --type offline_boot --settles CFG-001
goalforge standards gate --type route_restore --settles UX-004 --produces route,screenshot
goalforge verify record --check offline_boot --status PASSED --actual true --kind integration --output "..."
goalforge standards settle
```

```
$ goalforge standards settle
[v]  CFG-001

$ goalforge standards status
충족 1 · 미충족 0 · 일부 0 · 미확인 27 · 적용 제외 0
```

### 게이트가 무엇을 정산하는지는 선언해야 합니다

게이트와 기준을 **종류만으로** 맺으면, 아무 여정 테스트나 모든 여정 기준을 정산하게 됩니다. 빌드 게이트가 여정 기준을 정산하는 것과 같은 실수가 한 층 위로 올라간 것입니다 — 초록색인 무언가가 돌았고, 그것이 이 기준에 관한 것인지는 아무도 확인하지 않았습니다.

```
$ goalforge standards gate --type x --settles CFG-999
error: CFG-999: no such criterion in go-react-offline-service@0.1
```

없는 기준을 가리키는 연결은 아무것도 정산하지 못하면서 커버리지처럼 보입니다. 오타도 거절합니다.

### 게이트 종류와 근거

| 게이트 종류 | 만들어 내는 근거 |
| --- | --- |
| `journey` | `browser_test_result` |
| `integration` | `integration_test_result` |
| `security` | `security_test_result` |
| `build` | `build_log` |
| `test` | `test_result` |
| `performance` | `performance_result` |

`review` 는 없습니다. 사람의 판단이고, 그것을 실행 근거로 기록하면 **"누가 봤다"** 가 **"누가 돌렸다"** 자리에 서게 됩니다.

`--produces` 로 게이트가 추가로 만들어 내는 근거를 적습니다. 경로를 밟고 화면을 찍는 여정 러너는 `route` 와 `screenshot` 도 만들어 냅니다 — 적지 않으면 그것을 요구하는 기준은 영원히 정산되지 않습니다.

**종류가 맞지 않는 게이트는 선언해도 믿지 않습니다.** 빌드 게이트에 `--produces browser_test_result` 를 붙이는 것은 원래의 실수를 명시적으로 저지르는 것이고, 명시적인 버전도 거절해야 합니다. 위치를 가리킬 뿐인 근거(`route`, `commit_sha`)는 어떤 주장도 하지 않으므로 그대로 통과합니다.

### 설정과 실행은 다릅니다

게이트를 연결만 하고 돌리지 않으면 기준은 **그대로 있습니다.**

돌리지 않은 것을 통과로 보면 설정 파일을 고쳐서 기준을 충족시킬 수 있게 되고, 실패로 보면 아무도 확인하지 않은 일을 망가진 일로 보고하게 됩니다.

### 증명된 기준은 카드가 되지 않습니다

```
$ goalforge standards assess --supply
공급: NET-002, REL-001        ← CFG-001 은 게이트가 통과를 증명했으므로 빠집니다
```

게이트를 먼저 정산하고 그다음에 정적 읽기를 적용합니다. 약한 방법이 강한 방법의 답을 지우면 안 됩니다.

## 저위험 자동 구현

```sh
goalforge standards autonomy --enable \
  --standards NET-002 --scopes "web/**" --max-tokens 20000 --daily-limit 3
```

기본값으로 자동 승인은 **"실행해도 된다" 까지**입니다. `--merge` 또는 `--full` 을 붙이면 검증이 끝난 작업의 병합 승인까지 자동으로 합니다.

둘이 별개의 스위치인 이유: 실행 승인은 변경을 자기 worktree 안에 두고, 병합 승인은 모두가 빌드하는 브랜치에 올립니다. 앞을 원한 사람이 뒤를 조용히 얻으면 안 됩니다.

### 판정할 수 없는 일은 승인하지 않습니다

```
$ goalforge standards autonomy --enable --standards NET-002,REL-001 --scopes "web/**"
보류 WORK-…860693372: CFG-001 를 정산할 게이트가 없어 결과를 판정할 수 없습니다
보류 WORK-…863896880: NET-002 를 정산할 게이트가 없어 결과를 판정할 수 없습니다
보류 WORK-…867311990: REL-001 를 정산할 게이트가 없어 결과를 판정할 수 없습니다

$ goalforge standards gate --type asset_scan --settles NET-002
$ goalforge standards autonomy --enable --standards NET-002,REL-001 --scopes "web/**"
자동 승인: WORK-…863896880
보류 WORK-…860693372: CFG-001 를 정산할 게이트가 없어 결과를 판정할 수 없습니다
```

이것이 가장 중요한 규칙입니다. 아무것도 판정할 수 없는 일을 승인하면, 기계가 코드를 쓰고 어떤 게이트도 그것이 동작했는지 말하지 못합니다. 변경은 **시도되었다는 이유로** 완료로 들어갑니다.

### 봉투

| 조건 | 어기면 |
| --- | --- |
| 자동 승인이 켜져 있다 | 기본값은 꺼짐 — 도는 기본값은 아무도 고르지 않은 기본값입니다 |
| 기준이 허용 목록에 있다 | 빈 목록은 아무것도 허용하지 않는 목록입니다 |
| 변경 범위가 허용 범위 안이다 | 범위 없는 작업은 거절합니다 — 어디든 닿을 수 있는 것이 봉투의 반대입니다 |
| 크기가 한도 안이다 | |
| 위험도가 높지 않다 | 봉투는 자동화가 **어디서** 움직여도 되는지를 말할 뿐, 거기 있는 것이 다 안전하다는 뜻이 아닙니다 |
| 공급기가 접수한 일이다 | 사람이 쓴 일은 공급기가 승인할 것이 아닙니다 |
| 이전 자동 시도가 실패하지 않았다 | 막았던 것이 그대로 있고, 똑같은 두 번째 시도는 같은 자리에 도달하려고 예산을 씁니다 |

각 조건을 따로 검사해서 거절 사유가 **어느 것이었는지** 말합니다. "정책에 맞지 않습니다" 는 읽는 사람을 정책 문서로 보내 어느 부분인지 찾게 만듭니다.

### 병합까지 자동으로

```sh
goalforge standards autonomy --full
```

`--full` 은 `--enable --all-standards --all-scopes --merge` 와 같습니다. 네 개로 나눠 적으면 셋만 켜 놓고 왜 아무것도 안 움직이는지 의아해하게 됩니다.

```
$ goalforge standards autonomy --full
실행 자동 승인: WORK-…508734667, WORK-…511564050
실행 보류 WORK-…514700064: REL-001 를 정산할 게이트가 없어 결과를 판정할 수 없습니다
병합 자동 승인 대상이 없습니다
```

병합 승인은 실행 승인보다 요구가 좁습니다. 이 지점을 지나면 변경이 worktree 를 떠나 모두가 빌드하는 브랜치에 올라가기 때문입니다.

| 추가 조건 | 이유 |
| --- | --- |
| 작업이 `DONE` 이고 검증된 커밋이 있다 | |
| **그 커밋을 만든 실행에서** 정산 게이트가 모두 통과했다 | 다른 작업의 나중 실행이 통과한 것은 이 변경에 대해 아무 말도 하지 않습니다 |
| 돌지 않은 게이트가 없다 | 아무도 실행하지 않은 게이트를 근거로 내보내는 것은 미검증을 내보내면서 옆에 초록색 체크를 붙이는 것입니다 |
| 기본 브랜치의 통합 검증이 실패 상태가 아니다 | 깨진 브랜치 위에 쌓으면 무엇이 깨뜨렸는지 묻힙니다 |
| 공급기가 접수한 일이다 | 사람이 쓴 일은 자동화가 내보낼 것이 아닙니다 |

**"돌지 않았다" 와 "돌았는데 실패했다" 는 다른 문제이고 고치는 방법도 다릅니다** — 하나는 빠진 실행이고 하나는 깨진 코드라, 거절 사유가 어느 쪽인지 말합니다.

승인은 **평범한 범위 승인**입니다. 사람의 승인과 같은 요청·승인 경로를 지나고, 같은 감사 사슬에 들어가고, 같은 커밋에 고정됩니다. `goalforge merge` 는 차이를 알 수 없고 `integrity verify` 도 마찬가지입니다 — 기계가 만들었다고 기록이 나빠지지 않습니다.

승인한 커밋이 아닌 다른 커밋은 내보내지 못합니다:

```
error: APR-… was granted for commit dddddddddddd but WORK-… now points at eeeeeeeeeeee;
       review the new change and request approval again
```

### 기록

모든 자동 승인은 무엇이 그것을 허용했는지와 함께 기록됩니다.

```
기준 NET-002 · 범위 web/** · 판정 게이트 asset_scan
```

규칙으로 되짚을 수 없는 승인은 아무도 하지 않은 승인과 구별되지 않습니다.

실패한 시도는 사유를 보존합니다. 사유 없는 실패는 다음 읽는 사람 — 사람이든 자동화든 — 에게 이미 한 번 잘못된 것을 처음부터 알아내게 합니다.

하루 한도는 성공 여부와 무관하게 소모됩니다. 성공만 세는 한도는 매번 실패하는 루프를 무제한으로 돌게 합니다.
