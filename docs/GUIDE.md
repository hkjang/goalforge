# GoalForge 사용 가이드

기준 버전: v0.45.0

이 문서는 GoalForge 를 **처음부터 끝까지 한 번 돌려 보는 순서**로 쓰여 있습니다. 명령어의 전체 목록은 `goalforge` 를 인자 없이 실행하거나 [README](../README.md) 를 보세요.

---

## 0. GoalForge 가 하는 일과 하지 않는 일

GoalForge 는 목표를 받아 작업으로 나누고, AI 세션이 그 작업을 격리된 작업 공간에서 구현하게 하고, 검증 게이트로 판정하고, 증거를 남기고, 승인을 받아 반영합니다.

**하지 않는 일**을 먼저 아는 편이 낫습니다.

- 모델이 "완료했다"고 말하는 것을 완료로 받아들이지 않습니다. 완료는 **현재 산출물에서 필수 조건이 증거로 입증될 때**만 성립합니다.
- 승인 없이 기본 브랜치에 반영하거나 원격에 push 하지 않습니다.
- 판정 방법이 없는 요구를 완료로 처리하지 않습니다. 미확정으로 표시하고 남깁니다.

## 1. 설치와 첫 진단

[releases](https://github.com/hkjang/goalforge/releases) 에서 플랫폼에 맞는 압축 파일을
내려받아 풀면 실행 가능한 바이너리 하나가 나옵니다. 별도 런타임이나 Go 툴체인은
필요하지 않습니다.

```sh
tar -xzf goalforge_vX.Y.Z_linux_amd64.tar.gz
sha256sum -c SHA256SUMS --ignore-missing   # 같은 릴리즈의 체크섬으로 검증
./goalforge version
goalforge doctor
```

`version` 은 상태 데이터베이스를 열기 전에 답합니다. 내려받은 바이너리에 가장 먼저 하는
질문이 "이게 뭔데"이고, 그 답은 아직 프로젝트를 고르지 않은 디렉터리에서도 나와야 합니다.

`doctor` 는 두 가지를 따로 확인합니다.

- **환경**: git, 제공자 CLI, 어댑터가 쓰는 플래그 지원 여부, 인증
- **준비 상태**: 이 프로젝트가 **끝날 수 있는지**

플래그 확인은 CLI 자신의 도움말을 읽습니다. 이때 **서브커맨드 도움말까지** 읽습니다 —
`codex` 의 `--json`·`--output-schema` 는 `codex exec --help` 에, `opencode` 의 `--format` 은
`opencode run --help` 에만 있기 때문입니다. 그리고 도움말에서 못 찾은 플래그는 **차단하지
않고 경고로** 보고합니다. `qwen --approval-mode` 는 실제로 동작하지만 어느 도움말에도
나오지 않습니다 — 문서에 없다는 것이 CLI에 없다는 뜻은 아닙니다.

```
WARN qwen flags  도움말에서 확인하지 못한 플래그: --approval-mode (읽은 도움말: qwen --help)
```

두 번째가 조용히 틀리는 쪽입니다. 완료 조건에 같은 이름의 게이트가 없으면 증거가 영원히 쌓이지 않아 목표가 끝나지 않는데, 모든 지표는 건강해 보입니다.

```
FAIL criteria coverage  완료 조건 latency_p95 을(를) 측정하는 게이트가 없어 증거가 영원히 쌓이지 않습니다
FAIL proof kind         완료 조건이 요구하는 검증 종류와 게이트가 다릅니다: note_saves (journey 필요, 게이트는 build)
WARN proof kind         동작을 확인하는 게이트가 없어 빌드만 통과해도 완료로 판정될 수 있습니다
```

두 번째 `proof kind` 가 그중 가장 건강해 보이는 오설정입니다. 게이트도 있고 이름도 맞고 통과도 하는데, **측정한 것이 조건이 묻는 것이 아닙니다.**

## 2. 프로젝트 등록

```sh
goalforge project init --name myapp --provider claude --model sonnet \
  --worktrees --auto-commit
goalforge project profile team          # 예산·동시성·복구 한도를 한 번에
```

`--worktrees` 는 각 작업을 별도 worktree 에서 실행합니다. 켜 두세요. 작업이 서로의 파일을 밟지 않고, 검증이 무엇을 측정했는지가 명확해집니다.

웹에서 시작하려면 `goalforge serve` 후 `#/new` 의 설정 마법사를 쓰면 됩니다. 저장소 선택 → 환경 진단 → 목표 → 완료 조건 → 실행 정책 순서이며, 차단 문제가 있으면 다음 단계로 넘어가지 않습니다.

## 3. 목표를 판정 가능한 형태로

### 주제에서 초안을 받기

```sh
goalforge goal draft --topic "URL 단축 서비스: 긴 URL 을 짧은 코드로 바꾸고, 그 코드로 원래 URL 로 리다이렉트한다"
```

아래는 **빈 Go 저장소에 실제 제공자로 돌린 출력**입니다(일부만).

```
제목: URL 단축 서비스: 단축·리다이렉트·검증·동시성·E2E 게이트
목적: 긴 URL을 POST /shorten 으로 보내면 짧은 코드를 돌려주고, GET /{code} 가
      원래 URL로 302 리다이렉트하는 HTTP 서비스를 구현한다.

완료 조건 5개 (2회 시도):
  redirect_api_test exit code = 0 이고 TestRedirect 가 PASS (등록된 코드는 302 +
    Location=원래 URL, 미등록 코드는 404)  [test]
       게이트: go test -count=1 -v -run ^TestRedirect$ main.go main_test.go  (지금 실패함)
       main_test.go 가 없어 go test 가 파일을 찾지 못해 실패하고, 리다이렉트 핸들러도
       아직 구현되지 않았다.
  concurrency_race_free exit code = 0, 데이터 레이스 경고 = 0건 (TestConcurrent:
    100 고루틴이 동시에 단축·조회해도 코드 충돌과 레이스가 없음)  [test]
       게이트: go test -race -count=1 -v -run ^TestConcurrent$ main.go main_test.go  (지금 실패함)
       ...

이대로 설정하려면 같은 명령에 --apply 를 붙이세요. 확인은 사람이 합니다 —
자기 합격선을 스스로 정한 기계는 무엇과도 비교된 적이 없고, 자기와 합의했을 뿐입니다.
```

`--apply` 뒤에는 `goalforge plan` 의 차단이 바뀝니다.

```
OK    gates                  6개 중 필수 6개가 실행 후 검증합니다
BLOCK work item              실행할 수 있는 작업이 없습니다 (goalforge ideas 또는 replan)
```

**게이트가 없어서 아무것도 못 하던 상태는 여기서 끝납니다.** 다음 막는 것은 백로그이고, 그것은 `goalforge ideas` 의 일입니다.

완료 조건과 **그것을 정산할 게이트를 함께** 제안합니다. 따로 물으면 바람의 목록과 스크립트의 목록이 나오고, 둘이 만나지 않는다는 것은 일을 판정하려 할 때 알게 됩니다.

#### 지금 통과하는 게이트는 게이트가 아닙니다

제안된 게이트를 **현재 트리에 대고 돌려 봅니다.** 아직 만들지 않은 것을 재는 명령이 지금 통과한다면 내일도 통과하고, 그 기준은 아무도 아무것도 쓰기 전에 충족됩니다 — 목표가 만들어지는 순간 완료입니다.

위 실행도 **2회 시도**였습니다. 첫 초안이 심사를 통과하지 못해 반대 사유를 받고 다시 썼습니다.

#### 완료 조건과 건강 게이트는 다른 것입니다

초안은 둘을 **함께** 내놓습니다.

```
완료 조건 4개 (2회 시도):
  redirect_behavior exit code =0  [test]
       게이트: go test -count=1 -run ^TestRedirect$ ./shortener  (지금 실패함)
  ...

매 실행 뒤 통과해야 하는 게이트 (이것만 실행을 막습니다):
  go_vet exit code =0  [build]
       게이트: go vet ./...  (지금 통과함)
       현재 main.go 는 유효한 코드라 go vet 이 지금 통과한다. 컴파일 오류를 만드는 변경이 이를 깨뜨린다.
```

**검증 게이트는 매 작업 항목 뒤에 돌아가 "이번 변경이 무언가를 깨뜨렸는가" 를 묻고, 완료 조건은 "목표가 끝났는가" 를 묻습니다.** 완료 조건을 필수 게이트로 설치하면 기능이 여섯 개인 목표에 어떤 단일 작업도 통과시킬 수 없는 게이트가 여섯 개 생깁니다 — 첫 작업이 한 조각을 만들어도 전체를 요구하는 여정 게이트는 여전히 실패하므로, **모든 실행이 실패하고 복구 시도를 소진하고 프로젝트가 막힙니다.** 여러 조각으로 된 목표는 한 걸음도 나아갈 수 없습니다.

그래서 완료 조건 게이트는 **측정만** 합니다(필수 아님). 목표 진행도는 그 측정에서 읽습니다. 실행을 막는 것은 건강 게이트 하나뿐입니다.

| | 지금 | 종류 | 실행을 막는가 |
| --- | --- | --- | --- |
| 완료 조건 | **실패해야** 한다 | test·journey·security·performance 등 | 아니오 (측정만) |
| 건강 게이트 | **통과해야** 한다 | build 또는 test | 예 |

#### 테스트가 없어도 통과하는 게이트는 게이트가 아닙니다

```
$ go test -count=1 -run '^TestRedirect$' ./shortener
?   example.com/v/shortener  [no test files]
exit=0
```

`go test` 는 테스트 파일이 없는 패키지에서 **exit 0** 입니다. 걸러낸 실행도 맞는 검사가 없으면 "no tests to run" 과 함께 통과합니다. 초안 시점에는 패키지가 없어 게이트가 실패하므로 "지금 실패함" 규칙을 만족하지만, **세션이 빈 패키지만 만들면 통과**하고 그 기준은 초록이 됩니다 — 아무도 구현하지 않은 기능에 완료가 집계됩니다.

"지금 실패함" 이 증명한 것은 "디렉터리가 없으면 실패한다" 였고, 그것은 "기능이 동작할 때까지 실패한다" 보다 훨씬 약합니다.

그래서 **테스트를 돌리는 게이트는 그 검사가 실제로 실행됐음을 확인해야** 합니다.

```
gate_command:  ["go","test","-count=1","-v","-run","^TestRedirect$","./shortener"]
value_pattern: "--- PASS: (TestRedirect)"
expected_value: "TestRedirect"
```

없으면 초안이 거절됩니다. `-v` 없는 걸러낸 실행도, 걸러낸 이름을 담지 않은 패턴도 거절됩니다 — 다른 줄에 맞는 패턴은 검사가 없어도 통과하면서 확인된 것처럼 보이게 합니다.

빈 패키지에서 실제로 돌려 본 결과:

```
FAILED  redirect_behavior  exit=0  검사가 하나도 실행되지 않았습니다.
                                   이 기준을 재는 테스트를 먼저 작성해야 합니다 —
                                   명령이 통과한 것은 실행할 것이 없었기 때문입니다.
```

명령은 `exit 0` 인데 게이트는 실패입니다. 그리고 이 실패는 **코드 수정**으로 분류됩니다(사람이 고칠 것이 없습니다) — 루프가 빠진 테스트를 씁니다. 단, 한 패키지는 테스트가 없고 다른 패키지의 검사가 실패한 출력은 **테스트 실패**로 남습니다. "빠진 테스트를 써라" 는 지시를 받은 세션이 이미 빨간 테스트를 두고 새 테스트를 쓰면 안 됩니다.

#### 검증된 작업은 기본 브랜치에 올라가야 측정됩니다

작업 항목마다 **자기 worktree 에서** 구현되고 검증됩니다. 그래서 e2e 조건은 어떤 단일 worktree 에서도 통과할 수 없고 — 다른 조각이 거기 없습니다 — **완료 조건은 합쳐진 기본 브랜치에서 측정됩니다.**

```sh
goalforge merge --list          # 병합을 기다리는 검증된 작업
goalforge merge --all           # 전부 병합 (커밋마다 승인은 그대로 필요)
goalforge verify integration    # 기본 브랜치에서 게이트를 돌려 완료 조건을 측정
```

`status` 의 "Needs you" 에도 올라옵니다. 이것이 보고되지 않으면 작업이 worktree 에 남고, 손으로 합치지 않는 한 **목표는 영원히 미완**입니다.

```
$ goalforge verify integration
main 통합 검증: 필수 게이트 통과 (99cb1b442556)
아직 충족되지 않은 완료 조건 1개: redirect_behavior
브랜치는 깨지지 않았지만 목표는 끝나지 않았습니다 — `goalforge status` 로 각 조건의 상태를 봅니다
```

**"통합 검증 통과" 는 "목표 완료" 가 아닙니다.** 필수 게이트는 브랜치가 깨지지 않았다고 말하고, 완료 조건은 목표가 끝났는지 말합니다. 둘을 한 문장으로 보고하면 아무것도 구현되지 않은 목표에 성공이 보고됩니다.

두 검사는 **방향이 반대**이고 둘 다 실제로 돌려 확인합니다. 건강 게이트가 지금 실패하면 거절합니다 — 그것은 잘못된 이름을 단 완료 조건이고, 필수로 설치하면 목표가 끝날 때까지 모든 실행을 막습니다. 항상 통과하는 명령도 거절합니다: 아무것도 잡지 못하는 유일한 필수 게이트입니다.

게이트 명령에는 **셸을 쓸 수 없습니다.** `sh -c "a && b"` 는 거절됩니다 — 두 명령이 필요하면 그것은 기준이 둘이라는 뜻이고, 하나의 게이트가 하나를 재야 판정을 귀속할 수 있습니다.

#### 실제로 돌려 본 결과

빈 Go 저장소에 주제만 주고 돌린 한 바퀴:

```
goal draft --topic … --apply   완료 조건 5개 + 건강 게이트 go vet ./...
ideas                          작업 5건 (범위가 전부 경로 목록)
continue                       passed=true  progress=20%
continue                       passed=true  progress=40%
continue                       passed=true  progress=60%
continue                       passed=true  progress=80%
```

네 작업이 각각 건강 게이트를 통과하며 진행됐습니다. 다섯 번째는 세션이 추가한 import 의 모듈을 받아오지 못해 `go vet` 이 실패했고, **환경 문제로 분류되어** 사람에게 올라갔습니다 — 폐쇄망에서는 맞는 결과이고, 모델을 다시 돌려 해결되는 일이 아닙니다.

실제 제공자로 돌릴 때 눈여겨볼 한 가지: 빈 저장소에서는 제안된 게이트가 대개 **테스트 파일이 아직 없어서** 실패합니다. 그것도 "지금 통과하지 않는다" 의 증거이기는 하지만 약한 증거입니다 — 돌릴 수 없는 명령과 구별되는 것은 종료 코드뿐이고, 기능이 없어서 실패하는 것과 파일이 없어서 실패하는 것은 구별되지 않습니다. **사람의 확인이 그래서 남아 있습니다.**

| 거절 | 이유 |
| --- | --- |
| 항상 통과하는 명령 (`echo`·`true`·`:`) | 쓰이는 순간부터 초록이고 모든 변경을 지나 초록으로 남습니다 |
| 지금 이미 통과하는 게이트 | 아직 만들지 않은 것을 재고 있지 않습니다 |
| 돌릴 수 없는 명령 | 실패가 아닙니다 — 오타가 측정을 대신하게 됩니다 |
| 비교할 수 없는 기대값 | "잘 동작함" 은 문장이지 임계값이 아닙니다 |
| 게이트 없는 기준 | 나중에 말다툼할 문장입니다 |

#### 확인은 사람이 합니다

`--apply` 를 붙이기 전에는 아무것도 쓰지 않습니다. **자기 합격선을 스스로 정한 기계는 무엇과도 비교된 적이 없고, 자기와 합의했을 뿐입니다.**

이것이 "주제만 말하면 완성까지" 가 한 번의 확인을 남기는 이유입니다. 구현이 모자라서가 아니라, 그 확인이 나머지 전부가 의미를 갖는 근거이기 때문입니다.

---

완료 조건만으로 충분한 경우:

```sh
goalforge goal set --title "결제 실패율 개선" --objective "재시도 로직을 고친다" \
  --criterion build_passed=true --criterion coverage=85
```

수치 조건은 **방향과 단위를 함께 적습니다.** 방향을 적지 않은 숫자는 "이상" 으로 읽힙니다.

```sh
goalforge goal set --title "응답 속도" --objective "느린 화면을 고친다" \
  --criterion p95_latency_ms@performance="<=200ms" \
  --criterion uptime@integration=">=99.9%" \
  --criterion error_count@test="=0"
```

| 적는 법 | 뜻 |
|---|---|
| `<=200ms` · `≤200ms` · `최대 200ms` · `at_most 200ms` · `200ms 이하` | 상한 |
| `>=99.9%` · `≥99.9%` · `최소 99.9%` · `at_least 99.9%` · `99.9% 이상` | 하한 |
| `=0` · `exactly 0` | 정확히 그 값 |
| `!=0` | 그 값이 아님 |
| `200` | **이상** |

방향이 없으면 상한을 하한으로 판정합니다. `p95_latency_ms` 의 기대값을 `200` 으로 적어두면 5000 이 측정되어도 충족으로 읽히고, 빨라지는 것이 목적이었던 목표가 가장 느린 상태에서 완료로 보고됩니다.

단위는 같은 계열(시간 `ns`~`h`, 바이트 `B`~`TB`, `%`) 안에서 환산합니다. `<=200ms` 는 `0.15s` 로 측정해도 충족이고 `3s` 로 측정하면 미충족입니다. 계열이 다르면 **판정을 거부합니다** — 200ms 를 150MB 로 판정하는 판정기는 지연 목표를 메모리 측정으로 종결시킵니다. 단위를 적지 않은 숫자는 그 지표의 단위로 읽어 어떤 단위와도 비교됩니다.

미충족은 무엇을 기대했고 무엇이 측정됐는지를 함께 보고합니다.

```
[ ]  p95_latency_ms   기준 <=200ms   측정 5000ms   200ms 이하 를 기대했는데 5000ms 입니다
[ ]  memory_mb        기준 <=2MB     측정 1s       단위가 다릅니다: 기대 2MB 이하, 측정 1s — 같은 단위로 측정해야 판정할 수 있습니다
[ ]  uptime           기준 >=99.9%   측정 —        검증이 TIMEOUT 로 끝나 측정값이 없습니다
```

마지막 줄이 따로 있는 이유: 게이트 자체가 실패했으면 그것이 찍은 숫자는 아무것도 측정한 값이 아닙니다.

조건 이름에 `@종류` 를 붙이면 **어떤 종류의 검증이라야 그 조건을 충족시킬 수 있는지**를 함께 못박습니다.

```sh
goalforge goal set --title "메모 앱" --objective "사용자가 메모를 저장할 수 있다" \
  --criterion build_passed@build=true --criterion note_saves@journey=true
```

종류는 `build`, `test`, `integration`, `journey`, `security`, `performance`, `review` 입니다. 화면이 다 만들어졌고 빌드도 초록이지만 저장 버튼이 모의 구현에 연결된 경우, 빌드 통과는 **사실이면서 아무것도 증명하지 않습니다**. `@journey` 를 요구하면 그 조건은 빌드 게이트의 통과로 충족되지 않고 `WRONG_KIND` 로 보고되며, 목표는 완료되지 않습니다.

```
[x]  note_saves       기준 true       측정 true    검증 종류 불일치: journey 종류의 검증이 필요하지만 build 게이트가 측정했습니다
```

- 더 강한 증거는 약한 요구를 충족시킵니다. 여정이 돌았다면 빌드는 이미 성공했기 때문입니다.
- `security` 와 `performance` 는 다른 어떤 검증으로도 대체되지 않는 별개의 속성입니다.
- 종류를 요구하지 않는 조건은 이전과 완전히 동일하게 동작합니다. 기존 프로젝트가 갑자기 미충족이 되지 않습니다.

요구가 모호하거나 여러 개일 때는 **계약**을 씁니다.

```sh
goalforge goal contract --title "상담 시스템" \
  --users "상담원" --scenarios "문의 접수부터 종료까지" \
  --outcome "login|gate:auth_tests|verification,handling_time" \
  --measure "p95=latency_ms<=200" \
  --exclude "결제 연동"
```

각 필수 결과는 **어떻게 판정되고 누가 판정하는지**를 함께 갖습니다. 둘 중 하나라도 없으면 미확정이고, **미확정이 하나라도 있으면 목표는 완료로 판정되지 않습니다** — 경고가 아니라 판정입니다. 서로 충돌하는 필수 결과가 있을 때도 같습니다: 달성 가능한 정의가 없는 목표는 작업이 얼마나 끝났든 완료가 아닙니다.

```
[v]  login            gate:auth_tests / verification
[?]  handling_time    판정 방법 또는 판정 주체가 없어 미확정

미확정 1건: 판정 방법과 주체를 정하기 전까지 이 목표는 완료로 판정될 수 없습니다.
```

둘 다 성립할 수 없는 요구는 **양쪽을 남긴 채** 상충으로 보고합니다. 어느 쪽을 바꿀지는 사람이 정합니다.

상충 판정은 각 요구를 만족하는 값의 구간으로 읽고 교집합이 비는지를 봅니다. 경계가 중요합니다:

- `>= 200` 과 `<= 200` 은 **정확히 200 에서 만나므로 상충이 아닙니다.** 이것을 상충이라고 하면 사람들이 검출기를 무시하는 법을 배웁니다.
- `> 200` 과 `<= 200` 은 만족하는 값이 하나도 없으므로 상충입니다.
- `= 0` 과 `>= 1` 도 상충입니다. 등식은 값이 하나인 구간입니다.
- 임계값의 단위도 환산합니다. `>= 1s` 와 `<= 200ms` 는 1 과 200 이 아니라 1000ms 와 200ms 로 비교됩니다.
- 계열이 다른 단위끼리는 상충을 **주장하지 않습니다.** 근거 없는 상충 하나가 진짜 상충 열 개를 무시하게 만듭니다.

계약을 바꾸면 사유와 결정자가 있는 새 버전이 생기고, 이전 버전은 자신이 요구했던 것을 그대로 유지합니다. **범위를 줄여도 과거 판정이 바뀌지 않습니다.**

### 공통 개발 기준

여러 프로젝트에 같은 요구를 적용할 때는 목표마다 조건을 다시 쓰는 대신 **공통 개발팩**을 고정합니다.

```sh
goalforge standards profile --list-packs                     # 이 빌드가 가진 팩
goalforge standards profile --attributes deployment=cli,release=binaries
goalforge standards status                                   # 이 프로젝트가 어디에 서 있는지
goalforge standards compare                                  # 같은 팩을 고정한 프로젝트들을 나란히
```

```
$ goalforge standards profile --attributes deployment=cli,release=binaries
적용: go-cli-tool@0.1 — 기준 12개 중 12개가 이 프로젝트에 적용됩니다
```

기준 하나가 무엇으로 정산되는지와 그러려면 어떤 근거가 필요한지를 함께 싣습니다. 프로필의 속성에 맞지 않는 기준은 이 프로젝트의 결함이 아니므로 현황에 나오지 않습니다 — AI 가 없는 프로젝트는 스트리밍 기준을 어기고 있는 게 아닙니다.

**판정은 위로 올라가는 실패만 막습니다.** 근거가 없거나, 있어도 내용이 비었거나, 실행이 아니라 추정이면 `MET` 이 아니라 `UNKNOWN` 입니다. `UNMET` 은 불필요할 수도 있는 작업을 만들고 `MET` 은 아무도 확인하지 않은 것을 내보냅니다.

**팩은 버전으로 고정되고 체크섬까지 함께 고정됩니다.** 새 팩 버전은 차이를 제안할 뿐 과거 판정을 다시 쓰지 않고, 팩을 갈아 끼우면 무엇이 추가·삭제·개정됐는지 말합니다. 기준이 개정되면 그 기준의 옛 판정은 `UNKNOWN` 으로 돌아갑니다 — 다른 문장에 대한 답은 지금 묻는 질문에 답하지 않습니다. 고정한 팩의 체크섬이 어긋나면 무인 순회는 그 프로젝트를 건드리지 않고 다시 고정하라고 말합니다.

자세한 내용은 [docs/STANDARDS.md](STANDARDS.md) 를 보세요.

## 4. 검증 게이트

게이트가 없으면 어떤 실행도 검증되지 않고, 목표는 완료될 수 없습니다.

```sh
goalforge verify template go-api        # 프로젝트 유형별 시작 묶음
goalforge verify gate add --type coverage \
  --command-json '["go","test","-cover","./..."]' \
  --success-value 85 --value-pattern 'coverage:\s+([0-9.]+)%' --kind test
```

**게이트에는 `--kind` 로 그 게이트가 무엇을 증명하는지 밝힙니다.** 템플릿이 넣는 게이트는 모두 `build`/`test` 입니다. 그 프로젝트의 사용자 작업이 실제로 끝나는지는 프로젝트마다 다르므로 템플릿이 대신 채울 수 없고, `doctor` 가 그 공백을 경고합니다.

```sh
goalforge verify gate add --type note_saves \
  --command-json '["./scripts/journey-save.sh"]' --kind journey
```

게이트의 종류를 바꾸면 그 게이트가 과거에 남긴 증거는 **재검증 대상이 됩니다.** 컴파일을 "여정"이라고 다시 이름 붙여 옛 빌드 결과를 여정 증거로 승격시킬 수는 없습니다.

**수치 조건에는 `--value-pattern` 이 필요합니다.** 없으면 게이트가 통과했을 때 설정값을 그대로 실측값으로 기록해, 커버리지 조건이 상수 두 개를 비교하게 됩니다. 패턴이 있으면 출력에서 실제 값을 뽑아 임계값과 비교하고, 측정값이 없으면 실패 처리합니다.

### 게이트는 세션이 자기 일을 확인하는 수단이기도 합니다

AI 세션은 **무인으로 돕니다.** 물어볼 사람이 없습니다. 그런데 코딩 에이전트는 편집을 자동 승인해도 **셸 명령은 따로 확인을 요구**합니다 — Qwen Code 의 `auto-edit`, Claude Code 의 `acceptEdits` 둘 다 그렇습니다. 그러면 세션이 끝내기 전에 프로젝트 테스트를 돌려 볼 수 없고, 코드를 쓰고 "다 했다" 고 보고하면 **게이트가 뒤늦게 알아냅니다.**

그래서 GoalForge 는 **프로젝트가 선언한 게이트 명령을 그대로 허용 목록으로 넘깁니다.**

```
qwen    --allowed-tools run_shell_command(go test),run_shell_command(go test -count=1 ./...)
claude  --allowedTools Bash(go test) Bash(go test *) Bash(go build) Bash(go build *)
```

**새 권한을 주는 것이 아닙니다.** 그 명령들은 어차피 게이트로 실행됩니다. 반대로 "안전한 명령 목록" 을 누군가 정해 넣는 것은 아무도 요청하지 않은 보안 결정을, 아무도 들여다보지 않는 자리에 두는 일입니다.

규칙:

| | |
| --- | --- |
| 게이트 명령 그대로 | `go test -count=1 ./...` — 자기를 판정할 그 명령을 돌려 볼 수 있습니다 |
| 실행 파일 + 하위 명령 | `go test` — 작업 중인 패키지만 좁혀 돌릴 수 있습니다 (`go test ./shortener`) |
| 첫 인자가 플래그면 줄이지 않음 | `python -m pytest -q` → `python` 은 `python -c` 까지 열어 줍니다 |
| 하위 명령이 모드인 도구만 줄임 | `go`·`cargo`·`npm`·`make` 등. 스크립트의 인자는 모드가 아닙니다 |
| 차단된 실행 파일은 제외 | 게이트에 `rm` 이 들어 있어도 허용되지 않습니다 |
| 계획 실행은 아무것도 허용 안 함 | 보기만 하는 모드에 셸을 미리 허용하면 그 모드는 이름표입니다 |

하위 명령으로 줄이는 것이 **왜 안전한가**: `test` 라는 하위 명령은 제가 안전하다고 판단한 것이 아니라 **프로젝트가 자기 일을 판정하는 명령으로 고른 것**입니다. 뒤에 오는 것은 보통 경로나 필터입니다. 그래서 `make -j4 test` 는 `make -j4` 로 줄이지 않습니다 — 플래그는 모드가 아니고, 그러면 Makefile 의 모든 타깃이 열립니다.

**체인 명령은 쪼개져 각각 검사됩니다.** `go test ./... ; rm -rf /` 는 뒷조각이 여전히 막히고, `$()`·백틱·`<()` 같은 명령 치환은 하드 거부입니다. 허용 목록이 좁은 이유가 그 둘입니다.

### 게이트를 격리해서 실행하기

게이트는 **세션이 방금 쓴 코드를 실행**합니다. 세션보다 더 신뢰할 근거가 없습니다.

```sh
goalforge project sandbox --mode docker --image golang:1.23 \
  --memory-mb 2048 --cpus 2
```

작업 공간만 마운트되고, 네트워크는 끊기며, 능력은 제거되고, 루트 파일시스템은 읽기 전용입니다. 기본값이 호스트인 이유는 **프로젝트의 툴체인을 실행하지 못하는 샌드박스는 없느니만 못하기** 때문입니다.

## 5. 작업을 넣고, 실행 전에 확인하기

```sh
goalforge work add --title "재시도 백오프 구현" --priority 90 \
  --scope "internal/payment/**" --estimated-tokens 12000 \
  --depends-on WORK-1,WORK-2
goalforge plan
```

`plan` 은 **아무것도 바꾸지 않고** 다음 실행이 무엇을 할지 보여 줍니다.

```
다음 작업: WORK-… 재시도 백오프 구현
  실행 가능한 후보 3건 가운데 우선순위가 가장 높습니다

OK    gates                  4개 중 필수 3개가 실행 후 검증합니다
OK    token budget           120k / 2000k 사용 (94% 남음)
WARN  acceptance             완료 기준이 없어 무엇이 끝인지 실행 세션이 판단하게 됩니다
OK    forecast               약 15000 토큰 — 직접 입력한 예상치
```

`BLOCK` 은 실행이 거부된다는 뜻이고, `WARN` 은 실행은 되지만 결과에 문제가 있다는 뜻입니다 — 대개 목표가 완료로 판정될 수 없다는 뜻입니다. 둘은 다릅니다.

## 6. 실행

```sh
goalforge continue                 # 작업 1건을 실행하고 검증
goalforge worker                   # 자율 실행 (예약된 작업을 처리)
goalforge run --until-quota        # 한도까지 연속 실행
```

실행 중 무슨 일이 일어나는지:

1. 격리된 worktree 를 준비하고, **검증 게이트 원본을 확보**합니다
2. 실행 프롬프트에 **컨텍스트 패키지**를 싣습니다 — 확정된 설계 결정, 변경 제약, 이 작업의 이전 실패, 검증 방법
3. 세션이 구현합니다
4. **게이트를 원본으로 되돌리고** 검증합니다. 세션이 자신을 판정할 게이트를 다시 썼다면 그것은 반영되지 않습니다
5. 통과하면 작업 브랜치에 커밋합니다. 기본 브랜치는 건드리지 않습니다

### 실패했을 때

실패는 분류됩니다.

| 분류 | 자동 재시도 |
|---|---|
| 테스트 실패, 빌드 실패, 기준 미달 | 예 (횟수·비용 한도 안에서) |
| 환경 문제, 의존성, 인증 | **아니오** — 모델 재실행은 예산만 씁니다 |
| 제한 시간 초과, 게이트 설정 오류 | 아니오 — 사람의 판단 필요 |

```sh
goalforge status                   # 무엇이 막혔는지
goalforge reproduce --run RUN-1 --out ./repro   # 같은 조건으로 재현
```

## 7. 상태 읽기

```sh
goalforge status
```

```
Progress: 66.7% (2/3 가중치, 폐기 1건 기준선 제외)
Criteria:
  [v]  build_passed   기준 true  측정 true   근거 RUN-… 09-27 14:02
  [~]  coverage       기준 85    측정 88     재검증 필요: verified code changed
Needs you:
  - 승인 대기: MERGE_BRANCH — … (goalforge approval approve APR-…)
  - 통합 검증 필요: 병합 후 … (goalforge verify integration)
```

- `[v]` 충족 · `[~]` 재검증 필요 · `[!]` 기준 미달 · `[ ]` 증거 없음
- **작업 진행률과 필수 조건 충족은 다른 지표입니다.** 100% 진행이어도 조건이 미충족이면 완료가 아닙니다.
- 증거는 **측정한 트리와 게이트**를 기록하므로, 코드나 게이트가 바뀌면 자동으로 재검증 대상이 됩니다

### 칸반으로 보기

`goalforge serve` 의 **보드** 탭은 같은 작업들을 열로 세워 보여 줍니다.

```
  백로그 12   실행 대기 3   진행 중 1   검증 중 0   작업 완료 8   보류 2
```

카드마다 우선순위, 선행·후행 작업 수, 막힌 이유, 마지막 검증 결과가 함께 붙습니다. 제목과 상태만 있는 보드는 왜 안 돌아가는지 알려고 카드를 하나씩 열게 만듭니다.

**엔진이 정하는 상태로는 사람이 끌어다 놓을 수 없습니다.** 진행 중·검증 중·완료는 실행과 게이트가 정합니다. 끌기 시작하면 서버가 허용한 열만 강조되고, 나머지에는 왜 안 되는지가 붙습니다. 드롭이 일단 되고 나서 튕기는 일은 없습니다.

```sh
$ goalforge work status WORK-3 --set DONE
error: 작업 완료는 실행·검증 엔진이 정합니다. 사람이 옮기면 하지 않은 검증을 했다고 주장하는 것이 됩니다
허용된 이동: APPROVED, BLOCKED, DISCARDED
```

같은 규칙이 CLI·API·MCP 에서 모두 같습니다. 한 화면에서만 지켜지는 금지는 규칙이 아니라 그 화면의 습관입니다.

두 사람이 같은 카드를 옮기면 **나중 사람은 거절당합니다.** 카드는 버전을 이고 다니고, 화면이 들고 있던 버전이 낡았으면 이동이 반려됩니다. 덮어썼다는 사실조차 모르는 일은 없습니다.

#### 완료와 출시는 다릅니다

`작업 완료` 는 **그 작업 자신의 검증이 통과했다는 뜻**입니다. 병합되었는지, 합쳐진 결과가 동작하는지, 내보내도 되는지는 그 다음 질문들이고, 카드에 별도 배지로 붙습니다.

| 배지 | 뜻 |
|---|---|
| 검증 완료 | 게이트는 통과했고 아직 병합되지 않음 |
| 병합 승인 대기 | 사람의 병합 승인을 기다리는 중 |
| 병합 반려 | 검토에서 반려됨 |
| 병합 진행 중 | 병합 결과가 아직 확정되지 않음 |
| 병합 실패 | 병합을 시도했으나 실패 |
| 병합됨 · 통합 검증 대기 | 병합됐지만 합친 결과는 아직 검증 안 됨 |
| 병합됨 · 통합 검증 실패 | 합친 결과가 동작하지 않음 |
| 출시 가능 | 병합됐고 통합 검증도 통과 |

열 하나가 이 여덟을 모두 뜻하면, 초록색 카드 뒤에서 기본 브랜치가 깨져 있어도 화면은 아무 말도 하지 않습니다.

병합됐지만 통합 검증 기록이 아예 없는 경우도 **출시 가능이 아닙니다.** 실패가 없다는 것에서 통과를 읽어내면 아무도 돌리지 않은 검사를 통과했다고 주장하는 셈입니다.

## 8. 검토와 반영

```sh
goalforge serve                    # 대시보드에서 변경 검토
goalforge approval request --action merge-branch --work-item WORK-1 --reason "..."
goalforge approval list
goalforge approval approve APR-1
goalforge merge --work-item WORK-1
goalforge verify integration       # 병합 결과를 다시 검증
```

**승인은 검토한 그 변경에만 적용됩니다.** 작업·커밋 SHA·적용 대상에 고정되므로, 검토 후 커밋이 바뀌면 재검토를 요구합니다.

병합은 기본 브랜치를 **미검증 상태로** 만듭니다. 각 작업은 자신의 worktree 에서만 검증됐고, 합친 결과는 아직 아무도 검증하지 않았기 때문입니다. `verify integration` 이 그것을 채웁니다.

**통합 검증이 실패로 끝난 브랜치에는 더 병합되지 않습니다.**

```
$ goalforge merge --work-item WORK-3
error: default branch failed integration verification: a1b2c3d4e5f6 에서 go build ./... failed
— 먼저 통합 검증을 복구하세요 (`goalforge verify integration`).
깨진 브랜치 위에 더 쌓으면 무엇이 깨뜨렸는지 묻힙니다
```

세 가지는 구분합니다.

- **아직 검증하지 않은 것은 막지 않습니다.** 방금 병합한 브랜치는 언제나 미검증입니다. 그걸로 막으면 제품이 전제하는 흐름 자체가 멎습니다. 막는 것은 **실행되어 실패로 돌아온** 검사입니다.
- **통합 수정 작업은 통과시킵니다.** 자기 해결책을 막는 게이트는 교착이고, 교착에서 빠져나오는 유일한 길은 게이트를 우회하는 것입니다.
- **`publish` 는 막지 않습니다.** 원격에 올리는 것은 기본 브랜치를 건드리지 않고, 그것이 다른 사람이 수정을 들여다볼 수 있는 유일한 행동입니다.

통합 검증이 실패하면 **통합 수정 작업이 만들어집니다.** 무엇이 어느 커밋에서 실패했는지 담긴 채 바로 집을 수 있는 상태로 들어갑니다 — 오류 메시지로 끝나면 아무도 배정되지 않고 브랜치는 출시 불가인 채 남습니다. 같은 미해결 통합에서 다시 실패하면 그 작업을 갱신하고, 해결된 뒤의 실패는 새 작업을 만듭니다.

반려할 때는 사유를 남기세요. 개별 반려가 아니라 **반복되는 이유**가 개선할 지점을 알려 줍니다.

```sh
goalforge approval reject APR-1 --category insufficient_evidence --note "커버리지 근거 없음"
```

### 작업의 변경 범위가 경로 목록이 아닐 때

변경 범위는 **파일 경로와 비교됩니다.** 그래서 범위가 문장이면 어떤 파일과도 맞지 않고, 세션이 쓴 모든 파일이 범위 밖으로 보고되어 그 작업은 **매번 실패합니다.**

```
$ goalforge continue
error: 이 작업의 변경 범위가 경로 목록이 아닙니다 ("handler.go 신설: JSON 본문 파싱, …")
       — 바꿀 파일 경로나 glob 을 쉼표로 구분해 적어야 합니다.
       `goalforge work scope --item IDEA-… --set <경로>` 로 고치세요
```

```sh
goalforge work scope --list-unusable                       # 실행될 수 없는 작업 찾기
goalforge work scope --item IDEA-… --set handler.go        # 고치기
goalforge work scope --item IDEA-… --set "internal/store/**,cmd/app/main.go"
```

범위 패턴은 쉼표로 여러 개를 적고, `*` 는 한 경로 단계 안에서만, `**` 는 단계를 몇 개든(0개 포함) 건너뜁니다: `internal/**` · `**/*_test.go` · `internal/**/x.go` · `**`(저장소 전체). 예전에는 단독 `**` 나 `a/**/b` 가 아무것도 매칭하지 못해 작업이 항상 범위 밖 변경으로 중단되었습니다.

**빈 범위는 형식 오류가 아닙니다.** 빈 범위는 "아무것도 바꾸면 안 된다" 는 의도적 결정이고, 그 경우에는 바뀐 파일 목록이 나옵니다. 처방이 다르기 때문에 두 실패를 구분합니다 — 하나는 "범위를 경로로 적어라", 하나는 "엉뚱한 파일을 바꿨다" 입니다.

`ideas` 가 만드는 작업의 범위는 이제 스키마가 경로 목록을 요구하므로 문장이 들어오지 않습니다. 그 전에 접수된 작업은 위 명령으로 고칩니다.

### 정책 위반으로 막힌 프로젝트 풀기

```sh
goalforge unblock --reason "변경 범위를 경로 목록으로 고쳤습니다"
```

정책 위반으로 멈춘 실행은 **체크포인트를 남기지 않습니다.** 그래서 `goalforge resume` 은 되돌릴 지점을 찾지 못하고, 원인을 고친 뒤에도 프로젝트는 계속 막혀 있었습니다.

- **이유는 필수입니다.** 막힘을 푸는 것은 무엇이 멈춰 세웠는지 처리됐다는 판단이고, 그 판단이 위반과 무시 사이에 있는 유일한 것입니다. 이유는 기록됩니다.
- 멈춘 실행이 `IN_PROGRESS` 로 남긴 작업은 **보드로 돌아갑니다.** 그러지 않으면 그 작업이 WIP 슬롯을 영구히 점유하고, 다음 실행은 "WIP 한도" 로 거부됩니다 — 막힘을 풀어도 아무것도 진행되지 않습니다.
- 범위가 아직 경로 목록이 아닌 작업이 남아 있으면 **경고합니다.** 그대로 실행하면 다시 막히고, 운영자는 그것을 "unblock 이 안 들었다" 로 읽습니다.

## 9. 사람이 직접 고칠 때

```sh
goalforge takeover --work-item WORK-1 --reason "설계를 직접 바꿔야 함"
# ... 직접 수정 ...
goalforge takeover return --work-item WORK-1 --summary "인증 흐름 재작성"
```

인계는 일시정지가 아닙니다. 실행 중이면 거부하고, 작업 공간 소유권을 넘기고, 자동화가 그 작업을 집지 않게 합니다. 반환할 때 **게이트를 다시 실행**합니다 — 손으로 고친 것도 검증을 면제받지 않습니다.

한 건을 인계받아도 **자동화는 다른 작업을 계속합니다.** 동시 구현 한도는 에이전트가 쥔 작업만 셉니다.

## 10. 증거와 인수인계

```sh
goalforge evidence export --out ./evidence
goalforge pr --work-item WORK-1          # 목표·조건·검증이 연결된 PR 본문
goalforge report --since 24h             # 무엇이 끝났고 무엇이 막혔는지
```

증거 묶음은 목표 버전과 변경 사유, 작업별 커밋과 게이트 측정값, 설계 결정, 승인 이력, **반려된 승인과 완화된 기준**까지 한 문서로 묶습니다. 외부 리소스를 전혀 불러오지 않는 자체 완결형 HTML 이라 메일로 보내거나 몇 년 뒤에 열어도 동작합니다.

좋은 소식만 담은 묶음은 실제로 일어난 프로젝트와 다른 프로젝트를 서술합니다. 그래서 불편한 기록도 남깁니다.

## 11. 설계 결정 남기기

```sh
goalforge decision add --title "세션 저장소" \
  --decision "세션은 SQLite 에 보관한다" \
  --scope "internal/session/**" \
  --alternatives "메모리: 재시작에 살아남지 못함" \
  --consequences "동시 접근은 WAL 로 처리"
```

기록된 결정은 이후 모든 실행 프롬프트에 실립니다. 새 세션이 같은 결론을 다시 도출하거나, 이미 합의된 구조를 임의로 뒤집는 일을 줄입니다. 결정은 삭제되지 않고 **다른 결정으로 대체**됩니다 — 무엇이 기각됐는지가 그것이 다시 제안되는 것을 막습니다.

### 오래된 결정이 사실로 굳지 않게

`--scope` 가 **이 결정이 어떤 코드를 두고 내려졌는지**를 못박습니다. 그 파일들이 바뀌면 결정은 **재확인 필요**로 표시됩니다.

```
$ goalforge decision list
DEC-2  ACCEPTED   [v] 문서는 마크다운
  md 를 쓴다
  범위: docs/**
DEC-1  ACCEPTED   [~] 세션 저장소는 SQLite
  sqlite 를 쓴다
  범위: internal/session/**
  기준 커밋 a2dce43b546b 이후 1개 파일이 바뀌었습니다: internal/session/store.go

재확인 필요 1건 — 실행 세션에는 '확인되지 않음'으로 전달됩니다
```

결정이 **지워지는 것이 아닙니다.** 왜 지금의 구조가 이런지에 대한 가장 좋은 기록이므로 계속 전달되되, **사실이 아니라 확인할 것으로** 전달됩니다.

`--scope` 를 비우면 그 결정은 프로젝트 전체에 대한 것으로 보아 **이후 어떤 변경이든** 재확인 대상이 됩니다. 맞는 판정이지만 신호가 무뎌지므로, 범위를 적는 편이 낫습니다.

### 맥락에는 믿을 수 있는 정도가 함께 갑니다

실행 세션에 전달되는 맥락은 항목마다 표시를 답니다. 날짜만으로는 세션이 무엇을 믿어야 할지 알 수 없습니다 — 3월에 적힌 메모가 명백히 틀려 보이지는 않으니까요.

| 표시 | 뜻 |
| --- | --- |
| `측정된 사실` | GoalForge 가 기록한 증거가 뒷받침합니다 |
| `결정` | 합의된 선택입니다. 임의로 뒤집지 말고 제안하세요 |
| `확인되지 않음` | ⚠ 에 적힌 이유로 지금도 유효한지 확인되지 않았습니다. **사실로 삼지 않습니다** |
| `규칙` | 이 실행에 적용되는 제약입니다 |

한 번도 측정되지 않은 완료 조건, 증거가 낡은 조건, 검증 종류가 어긋난 조건도 모두 `확인되지 않음` 으로 전달됩니다. 행이 아무리 자신 있게 읽혀도 측정된 사실이 아니기 때문입니다.

## 12. 구성 변경을 측정하기

프롬프트나 모델이나 정책을 바꿨을 때 **그 변경의 효과**를 알려면 고정된 과제가 필요합니다.

```sh
goalforge eval add --name "nil-deref" --kind bug_fix --objective "빈 입력에서 패닉이 나지 않는다"
goalforge eval spec --case EVAL-1 --fixture ./fixtures/bug1 --ref <commit> \
  --criterion build_passed=true --work "패닉 수정" \
  --gate-type build_passed --gate-command-json '["go","test","./..."]' \
  --token-budget 100000 --timeout-seconds 900
goalforge eval run --case EVAL-1 --label "sonnet-baseline" --repeat 3
goalforge eval compare --case EVAL-1
```

반복마다 **새로 클론한 작업 공간과 다른 시행을 본 적 없는 상태 DB** 에서 실행됩니다. 기준 상태에서 시작하지 않은 작업 공간은 측정 불가로 기록합니다 — 점수를 매기면 다른 과제를 측정하는 것이고, 버리면 유리한 실행만 남습니다.

보고는 **재실행 시행과 붙인 실행을 절대 합산하지 않고**, 반복 안정성을 단일 성공률과 나란히 보여 주며, 성공당 비용에 실패한 시도를 포함합니다.

### 실패를 과제로 바꾸기

개선 루프는 **실제 실패가 반복 가능한 측정이 되어야** 닫힙니다. 그전까지 "프롬프트를 고쳤다"는 **다시 돌릴 수 없는 실행에 대한 주장**입니다 — 저장소는 이미 움직였고 남은 것은 로그뿐입니다.

```sh
goalforge eval from-failure --run RUN-1          # 실패한 실행에서
goalforge eval from-failure --approval APR-1     # 사람이 반려한 승인에서
```

```
evaluation case created from run: EVAL-179056... (빌드 오류 수정 (build_failure) 09-28 12:52)
  고정: /repo @ 6487cf4ccc82
  완료 조건 1개, 게이트 1개, 초기 작업 1개
  실패 유형: build_failure
  이 과제가 통과하려면 build_passed 이(가) 통과해야 합니다 (원래 실패 유형: build_failure)
```

- **실행이 시작한 커밋에 고정합니다.** 현재 상태에 고정하면 이미 고쳐진 코드를 두고 묻는 셈이라, 통과해도 구성과 아무 상관이 없습니다.
- 그때 유효했던 **완료 조건·게이트·실패한 작업 항목**이 함께 고정됩니다. 요구하는 검증 종류도 따라갑니다 — 실패했던 실행보다 약한 기준으로 판정되면 안 되니까요.
- **실패 유형과 반려 사유 분류**가 기록됩니다. 그래야 과제 묶음이 "구성이 나쁘다"가 아니라 **"어디가 나쁘다"**를 말합니다.
- 통과한 실행으로는 만들지 않습니다(`--even-if-it-passed` 로 회귀 방지용은 가능). 통과하는 과제로만 찬 묶음은 **아무것도 측정하지 않으면서 커버리지처럼 보입니다.**
- **반려에서 만든 과제가 더 값집니다.** 게이트는 통과했는데 사람이 아니라고 한 것이므로, 게이트가 못 잡는 실패입니다.

시작 커밋을 기록하지 않은 실행은 **거부합니다.** 시작 상태가 없으면 다시 돌릴 과제가 아니라 과제에 대한 설명일 뿐이고, HEAD 에 고정해 놓고 측정이라 부르는 것이 막으려는 고장입니다.

### 기준선과 비교하기

"GoalForge 가 과제의 N% 를 완수한다"는 **GoalForge 에 대한 주장이 아닙니다.** 같은 방식으로 측정한 다른 무언가가 없으면 비교 대상이 없기 때문입니다. 기준선은 **같은 모델·같은 도구·같은 작업 공간·같은 예산으로, 같은 과제를 그냥 시켰을 때** 입니다 — 분해도, 검증-복구 루프도, 증거 원장도 없이.

```sh
goalforge eval run --case EVAL-1 --label "sonnet" --repeat 5                    # GoalForge
goalforge eval run --case EVAL-1 --label "sonnet" --repeat 5 --arm baseline     # 같은 조건, GoalForge 없이
goalforge eval compare --case EVAL-1
```

```
GoalForge vs 기준선 (같은 모델·도구·예산으로 GoalForge 없이)
  조건 a1b2c3d4e5f60718
    goalforge    성공률    80%  시행 5  성공당 비용 $2.5000  개입 0.0
    baseline     성공률    20%  시행 5  성공당 비용 $5.0000  개입 0.0
    차이         성공률 +60%p  성공당 비용 0.50x
    시행이 팔당 5건뿐입니다 — 방향을 시사할 뿐 수치로 인용할 수 없습니다
```

두 팔에서 **오직 시스템만 다릅니다.** 과제 문구, 예산, 작업 공간, 그리고 무엇보다 **판정자가 같습니다** — 같은 게이트를 같은 방식으로 측정하고, 완료 조건이 요구하는 검증 종류까지 똑같이 적용합니다. 기준선 프롬프트에는 게이트 명령까지 그대로 알려 줍니다. 숨기면 GoalForge 의 프롬프트를 측정하게 되고, 비교가 참이 아니라 유리해집니다.

비교가 성립하지 않으면 **수치를 내지 않고 이유를 말합니다.**

```
비교 불가 — 기준선 시행이 없습니다 — GoalForge 를 무엇과도 비교하지 않은 수치입니다
```

조건 해시는 **같이 놓고 볼 수 있는지**를 증명하는 장치입니다. 그래서 라벨과 팔(독립 변수)은 해시에서 빠지고, 고정물·커밋·완료 조건·게이트·검증 종류·예산·제한시간(같아야 하는 것)만 들어갑니다. 조건이 다른 두 팔은 비교하지 않고, 한 묶음 안에 조건이 섞여 있으면 그 평균은 해석할 수 없다고 표시합니다.

### 구성을 한 번에 하나씩 바꾸고, 통하지 않으면 되돌리기

측정 장치가 서면 구성 변경을 **추측이 아니라 탐색**으로 돌릴 수 있습니다. 전체 규칙은 [SELECTION.md](SELECTION.md) 에 있고, 한 회차는 이렇게 돕니다.

```sh
goalforge config calibrate --label base      # 측정이 저절로 얼마나 움직이는지 먼저 잰다
goalforge config draft --apply               # 모델이 다음 변경을 제안하고, 적용 가능하면 적용한다
# ... 바뀐 구성으로 평가를 돌린다 ...
goalforge config settle --incumbent base --candidate after
```

```
$ goalforge config settle --incumbent base --candidate wip4
[ ] NOT_SHOWN: 3 → 4
   지금까지 최고 100.0% 에서 노이즈 13.0%p 를 빼도 52.4% 에 못 미칩니다
   제안 PRP-… 에 기록했습니다
되돌렸습니다: wip_limit 를 3 로
```

- **노이즈를 재기 전에는 아무것도 판정하지 않습니다.** 측정이 저절로 얼마나 움직이는지 모르면 어떤 차이도 개선이라고 부를 수 없습니다.
- **한 번에 하나만 적용됩니다.** 판정 전에 둘을 적용하면 점수가 움직였을 때 무엇이 움직였는지 말할 수 없습니다.
- **측정이 뒷받침하지 못한 변경은 반드시 되돌아갑니다.** 실패한 채 남겨 두는 변경은 설정이 실패할 때마다 한 걸음씩 흘러가는 것입니다.
- **판정은 그 변경을 제안한 이력에 기록됩니다.** 그래서 성립하지 않은 설명은 다음 회차에 다시 뽑히지 않습니다 — 같은 말을 다르게 적은 것도 같은 설명으로 봅니다.
- 적용했으나 **아직 판정되지 않은** 제안은 성립한 것도 반증된 것도 아닙니다. 판정 불가(UNJUDGEABLE)도 마찬가지입니다 — 시행이 모자라 판정하지 못한 것은 가설에 대해 아무것도 말하지 않습니다.
- 되돌린 기록도 지우지 않습니다. 흔적 없이 되돌린 변경은 다음 회차가 기꺼이 다시 제안합니다.

`goalforge config changes` 로 자동화가 무엇을 바꿨고 무엇이 되돌아갔는지 봅니다.

## 13. 권한 경계

세션은 저장소를 바꿀 수 있지만 **무엇이 수용 가능한지를 결정하는 것**은 바꿀 수 없습니다.

제공자 프로세스와 검증 게이트는 역할 표시를 달고 실행되며, 그 안에서 시작된 것은 전부 상속합니다. 승인, 목표 변경, 게이트 변경, 예산·정책 변경, merge, publish, 평가 기준, 인계는 **CLI·MCP·HTTP API 어디서도** 거부됩니다.

### HTTP API 는 호출자를 확인할 수 없으면 결정하지 않습니다

`goalforge serve` 는 루프백에서 토큰 없이 뜹니다. 그 상태의 API 는 **아무도 인증하지 않습니다.** `X-Requested-With` 헤더는 브라우저의 교차 출처 요청을 막는 장치이지 **자격증명이 아닙니다** — curl 은 플래그 하나로 붙입니다. 그런데 GoalForge 가 돌리는 세션은 같은 기계에서 같은 포트에 닿습니다.

그래서 토큰이 설정되지 않은 API 는 **승인·목표 변경·예산 변경을 수행하지 않습니다.**

```
$ curl -X POST -H 'X-Requested-With: GoalForge' .../approvals/APR-1/approve
HTTP 403
{"error":"이 API 는 호출자를 확인할 수 없어 승인을 수행하지 않습니다.
          GOALFORGE_API_TOKEN 을 설정하고 다시 시작하거나, `goalforge approval approve <ID>` 로 수행하세요"}
```

**읽기는 그대로 열려 있습니다.** 실행을 지켜보는 것이 루프백 대시보드의 존재 이유이고, 그걸 닫아 봐야 막아지는 것은 없습니다.

토큰을 설정하면 호출자는 **세션에게는 절대 주어지지 않는 운영자 비밀**을 제시한 것이므로 결정이 허용됩니다. 대시보드는 401 을 받으면 토큰을 묻습니다.

```sh
export GOALFORGE_API_TOKEN='<운영자만 아는 값>'
goalforge serve
```

환경도 좁혀집니다. `PATH`, `HOME`, 제공자 자격증명 계열만 넘어가고 관련 없는 배포 토큰은 넘어가지 않습니다. 도구가 특정 변수를 꼭 필요로 하면:

```sh
export GOALFORGE_PASS_ENV=DEPLOY_TOKEN,REGISTRY_URL
```

## 14. 장애가 났을 때

```sh
goalforge effects --reconcile      # 바깥에 무엇을 했는지 정산
goalforge status
```

- **후속 작업 유실 없음**: 계속하겠다는 의도가 결과와 같은 트랜잭션에 기록되고, 워커가 시작할 때 작업으로 바뀝니다
- **중복 외부 변경 없음**: push·merge 는 원장을 거치고, 결과가 불명확하면 재시도 전에 원격에 실제 상태를 묻습니다. 확인할 수 없으면 **아무것도 재시도하지 않습니다**
- **오래된 워커 차단**: 임대가 만료되거나 취소되면 세대가 올라가고, 이전 세대의 확정은 거부됩니다

### 제공자가 바로 죽을 때

제공자 실패는 **제공자 자신의 stderr 와 종료 상태**로 보고됩니다.

```
error: /home/me/.local/bin/qwen exited: exit status 1
error: not logged in
```

예전에는 `error: write |1: broken pipe` 가 나왔습니다. 제공자가 프롬프트를 다 읽기 전에 끝나면 쓰기가 깨지는데, 그것은 **원인이 아니라 결과**입니다 — 인증이 실패했는지, 플래그가 잘못됐는지는 제공자의 stderr 가 말합니다. 파이프 오류를 보고하면 읽는 사람이 GoalForge 의 배관을 들여다보게 됩니다.

같은 이유로, **일을 마치고 프롬프트를 읽지 않은 채 끝난 제공자는 실패가 아닙니다.** 예전에는 그것이 실패로 보고됐고, 쓰기가 종료와의 경쟁에서 지는지에 따라 같은 제공자가 성공이나 실패로 돌아왔습니다.

### 기록이 고쳐지지 않았는지 확인하기

GoalForge 의 주장은 전부 두 종류의 기록에 걸려 있습니다 — 목표가 끝났다고 말하는 **증거**, 그리고 변경을 내보내도 된다고 말하는 **승인**. 그런데 GoalForge 가 돌리는 세션은 같은 데이터베이스 파일에 쓸 수 있습니다. **GoalForge 가 쓴 행과 구분할 수 없는 행은 증거가 아닙니다.**

두 기록은 쓰일 때 추가 전용 사슬에 엮이고, 다음 명령이 대조합니다.

```sh
goalforge integrity verify
```

```
무결성 기록 42건
사슬 보호: 키 있음 — 기록을 고친 사람도 사슬을 다시 계산할 수 없습니다
결과: 기록이 GoalForge 가 쓴 그대로입니다
```

세 가지를 **서로 다르게** 보고합니다. 뜻이 다르기 때문입니다.

| 발견 | 뜻 |
| --- | --- |
| `RECORD_EDITED` | 기록된 뒤 행이 수정됨 — 상태·측정값뿐 아니라 **게이트 출력**까지 포함합니다 |
| `RECORD_MISSING` | 기록이 삭제됨 |
| `UNCHAINED_RECORD` | **GoalForge 를 거치지 않고** 데이터베이스에 직접 쓰임 |
| `CHAIN_BROKEN` | 사슬 자체가 다시 쓰임 (항목 수정·삽입·삭제) |

```
발견 1건:
  RECORD_EDITED     evidence  1   build_passed 증거가 기록된 뒤 수정되었습니다 (현재 build_passed=PASSED)
```

종료 코드가 0 이 아니므로 CI 에 그대로 걸 수 있습니다.

#### 키를 설정하세요

```sh
export GOALFORGE_AUDIT_KEY='<운영자만 아는 값>'
```

키가 없으면 사슬은 수정·삭제·무단 삽입을 **탐지는 하지만**, 데이터베이스에 쓸 수 있는 사람이 사슬 전체를 다시 계산하는 것까지는 막지 못합니다. 키가 있으면 링크가 MAC 이라 막습니다. `integrity verify` 는 둘 중 **무엇이 실제로 걸려 있는지 말합니다** — 더 강한 쪽을 암시하지 않습니다.

**게이트 출력도 보호 대상입니다.** 어떤 시험이 깨졌는지, 컴파일러가 뭐라고 했는지, 몇 번째 줄인지 — 사람이 결과를 믿을지 판단할 때 읽는 바로 그 텍스트입니다. 상태를 그대로 두고 사유만 "사소한 경고"로 바꾸는 것도 탐지됩니다.

출력이 보호되기 전에 기록된 증거는 **변조로 보고하지 않되 몇 건인지 알려 줍니다.** GoalForge 가 스스로 바꾼 것을 두고 늑대라고 외칠 수는 없고, 그렇다고 "이상 없음"에 섞어 넣을 수도 없습니다.

```
게이트 출력이 보호되지 않는 오래된 증거 3건 — 이 행들은 검증되지만, 실패 사유를 고쳐도 탐지되지 않습니다
```

이 키는 `GOALFORGE_API_TOKEN`, `GOALFORGE_MCP_TOKEN`, `GOALFORGE_POSTGRES_DSN` 과 함께 **어떤 실행 세션에도 전달되지 않습니다.** `GOALFORGE_PASS_ENV` 로 이름을 적어도, `GOALFORGE_INHERIT_ENV=all` 을 켜도 예외가 없습니다. 운영자가 환경을 넓히는 것은 "이 세션이 내 도구를 봐도 된다"는 뜻이지 "이 세션이 자기 감사의 열쇠를 쥐어도 된다"는 뜻이 아닙니다.

### 백업과 복원

```sh
goalforge backup --out ./state.backup
goalforge restore --from ./state.backup --to ./restored/state.db
```

백업은 파일을 그대로 복사하지 않고 SQLite 자체 메커니즘을 씁니다. 워커가 쓰는 중에 뜬 복사본은 **절반만 적용된 트랜잭션의 복사본**이기 때문입니다.

복원은 세 가지를 합니다. 살아 있는 상태를 덮어쓰지 않고, 복원된 기록이 백업 당시와 같은지 대조하며, GoalForge 가 바깥에 시작해 둔 것을 정산합니다. **미해결 push 를 둔 채 재개하는 것이 복원이 중복을 만드는 방식입니다.** 결과를 확인할 수 없는 효과가 하나라도 있으면 "safe to resume" 을 말하지 않고 멈춥니다.

## 15. 터미널에서 보기

브라우저 없이 같은 화면을 봅니다.

```sh
goalforge tui
```

```
결제 서비스  검증 중  작업 [████████████] 100.0%  조건 2/3  1/2 프로젝트
 1 개요   2 완료 조건   3 작업   4 승인   5 계획
  조건                   기준       측정       상태
  build_passed           true       true       ✓ 충족
  coverage               85         91.2       ✓ 충족
  retry_works            true       true       ✗ 검증 종류 불일치  journey 종류의 검증이…

  완료 아님: retry_works ✗ 검증 종류 불일치
```

**머리글이 작업 진행률과 조건 충족을 나란히 보여 주는 이유**가 이 화면의 핵심입니다. 작업 100% 에 조건 2/3 은 완료가 아닙니다. 둘을 따로 보여 주지 않으면 100% 가 "끝났다"로 읽힙니다.

| 키 | 동작 |
| --- | --- |
| `?` | 키 목록 (한 화면) |
| `1`–`5`, `Tab` | 탭 이동 (개요·완료 조건·작업·승인·계획) |
| `↑` `↓` / `j` `k` | 목록 이동 — **개요에서는 프로젝트 선택** |
| `←` `→` / `h` `l` | 프로젝트 전환 |
| `PgUp` / `PgDn` | 한 화면씩 |
| `Home` / `End` (`g` / `G`) | 처음 / 끝 |
| `a` / `x` | 승인 / 반려 (승인 탭) |
| `r` | 새로고침 |
| `q`, `Esc`, `Ctrl-C` | 종료 |

목록이 화면보다 길면 **커서를 따라 스크롤**하고, 안 보이는 줄이 몇 개인지 위아래에 적습니다. 화면에 들어오는 만큼만 그리고 나머지를 버리면 커서가 보이지 않는 곳에서 움직여서 **키가 안 먹는 것과 구분되지 않습니다.**

- **승인 결정은 화면을 연 시점이 아니라 결정하는 시점에 권한을 확인합니다.** `goalforge approval approve` 를 거부당하는 세션은 이 키도 거부당합니다. **화면을 여는 것은 권한이 아닙니다.**
- 승인 탭에서 선택한 항목 아래에 **무엇을 승인하는지**가 함께 나옵니다 — 작업, 커밋, 대상 브랜치, 바뀐 파일 수, 요청 시각.
- **기록 무결성에 문제가 있으면 모든 탭 위에 경고가 뜹니다.** 탭 하나에 숨기면 안 되는 종류의 소식이기 때문입니다.
- 계획 탭은 차단 항목을 **맨 위로** 올립니다. 초록 줄 아래에 묻힌 차단은 보고된 것이지 전달된 것이 아닙니다.
- 터미널이 아니면 매달리지 않고 이유를 말하며 종료합니다. `NO_COLOR` 를 따르고, 색 없이도 읽히도록 상태를 **글자로도** 표시합니다.
- 한글은 터미널에서 두 칸을 차지합니다. 열 정렬을 **표시 폭 기준**으로 계산하므로 한글 이름이 섞여도 어긋나지 않습니다.

```sh
goalforge tui --refresh 10s    # 기본 5초
```

## 16. 리눅스에서 서비스로 돌리기

워커를 계속 띄워 두려면 systemd 유닛이 필요합니다. 손으로 쓰면 **세 가지가 어긋납니다** — 실행 파일 경로, 상태 DB 경로, 작업 디렉터리. 특히 마지막 것이 조용합니다: 엉뚱한 디렉터리에서 시작한 워커는 **등록된 프로젝트를 못 찾고 빈 큐를 돌면서 완벽히 건강해 보입니다.**

```sh
cd /srv/myapp                      # 프로젝트가 등록된 디렉터리에서
goalforge service systemd --scope system | sudo tee /etc/systemd/system/goalforge-worker.service
```

유닛은 **실행 중인 프로세스에서 만들어지므로** 세 경로가 실제로 맞는 값입니다. 그리고 **설치하지 않고 출력합니다** — `/etc` 에 쓰는 것은 운영자의 결정이지, 유닛 내용을 물어본 것의 부작용이 아닙니다.

```ini
[Service]
ExecStart=/usr/local/bin/goalforge worker
WorkingDirectory=/srv/myapp
Environment=GOALFORGE_DB=/srv/myapp/.goalforge/goalforge.db
EnvironmentFile=-/etc/goalforge/worker.env
Restart=on-failure
TimeoutStopSec=300
NoNewPrivileges=yes
```

- **비밀값은 유닛에 쓰지 않습니다.** 유닛 파일은 누구나 읽을 수 있어서, 거기 적힌 토큰은 그 기계의 모든 계정에 공개한 것과 같습니다. `EnvironmentFile` 이 가리키는 파일에 적고 `chmod 600` 하세요 — `GOALFORGE_AUDIT_KEY`, `GOALFORGE_API_TOKEN`, `GOALFORGE_MCP_TOKEN`, `GOALFORGE_POSTGRES_DSN`.
- **`TimeoutStopSec=300`**: 세션을 도중에 죽이면 아무도 기록하지 않은 절반짜리 변경이 남습니다. 끝낼 시간을 줍니다.
- **`Restart=on-failure`**: 목표 중간에 죽은 워커는 돌아와야 합니다. 쥐고 있던 임대는 만료되고 작업은 다시 잡힙니다.

`--scope user` 로 하면 `systemctl --user` 용 유닛이 나옵니다(루트 권한 없이).

```sh
journalctl -u goalforge-worker -f
```

## 17. 저장소를 옮겼을 때

프로젝트는 **저장소 경로로 찾습니다.** 그래서 저장소를 옮기면 모든 명령이 "여기 프로젝트 없다"고 하는데, 목표·증거·승인은 전부 상태 DB 에 그대로 있습니다.

```
$ goalforge status
error: 현재 디렉터리 /srv/app-new 에 등록된 프로젝트가 없습니다.
등록된 프로젝트:
  myapp	/srv/app  (경로가 존재하지 않습니다)
저장소를 옮겼다면 `goalforge project relocate` 로 경로를 갱신하세요
```

"not found" 만으로는 **사실이지만 쓸모가 없습니다.** 무엇이 어디에 등록돼 있는지, 그 경로가 지금도 있는지가 다음 행동을 정합니다.

```sh
cd /srv/app-new
goalforge project relocate
```

**다시 등록하는 것이 아니라 이름을 바꾸는 것입니다.** 다시 등록하면 기존 프로젝트 옆에 두 번째가 생기고 이력은 그대로 남겨집니다. 프로젝트가 여러 개면 `--name` 으로 지정해야 합니다 — 어느 것이 옮겨졌는지 찍어서 맞히면 엉뚱한 기록을 고치게 됩니다.

이전 경로에 만들어진 worktree 는 따라오지 않습니다. 그 사실도 함께 알려 줍니다.
## 18. 데이터베이스가 커질 때

워커를 오래 띄워 두면 쌓입니다. **제공자가 내는 모든 이벤트가 통째로 저장되고, 지우는 곳이 없었습니다.**

```sh
goalforge storage usage
```

```
상태 데이터베이스: 2.0 MiB

  표                               행           본문
  event_logs                    300      1.2 MiB
  prompt_records                 50      146 KiB
  verification_results            0            —
```

**본문이 큰 쪽이 실제로 자라는 부분**입니다. 어디에 쓰였는지 보고 나서 정리하세요.

```sh
goalforge storage prune --older-than 30d              # 무엇이 지워질지만 보고
goalforge storage prune --older-than 30d --apply --vacuum
```

**본문만 버리고 행은 남깁니다.** 이벤트는 종류·시각·해시를, 프롬프트는 템플릿과 해시를 그대로 유지합니다. 그래서 감사는 **"무슨 일이 언제 있었는지"에는 계속 답하고 "정확히 어떤 문장이었는지"에만 답하지 못하게** 됩니다 — 기가바이트를 먹는 쪽이고 가장 덜 필요한 쪽입니다.

**검증 증거·승인·무결성 사슬은 건드리지 않습니다.** 목표의 완료가 거기에 걸려 있고, 무결성 사슬이 그것들을 덮고 있습니다. 하나라도 지우면 `integrity verify` 가 변조를 보고합니다 — 맞는 말이고 쓸모없는 말입니다.

- **기본은 보고만** 합니다. `--apply` 없이는 아무것도 지우지 않습니다. 오타로 지운 감사 자료는 돌아오지 않습니다.
- **끝나지 않은 실행은 건드리지 않습니다.**
- 빈 공간은 `--vacuum` 전까지 파일 시스템에 돌아오지 않습니다(데이터베이스 전체를 다시 씁니다). 위 예시에서 2.0 MiB → 492 KiB.
- 기간은 `30d`, `12w`, `720h` 를 받습니다.

## 19. 세션이 사라졌을 때

GoalForge 는 제공자 세션 ID 를 기억했다가 다음 실행에서 `--resume` 에 씁니다. 그런데 **그 ID 는 제공자 저장소에 대한 주장이지 GoalForge 저장소에 대한 주장이 아닙니다.** 제공자는 만료·캐시 정리·다른 기계 같은 이유로 언제든 그 세션을 버릴 수 있고, **재개를 요청받았을 때에야 그렇다고 말합니다.**

```
{"error":"qwen exited: exit status 1","message":"No saved session found with ID 32e113ab-..."}
```

이 경우 **연결을 끊고 새 세션으로 그 턴을 다시 수행합니다.** 대화 맥락은 어느 쪽이든 잃지만, 달라지는 것은 **목표가 멈춰 서서 사람을 기다리느냐**입니다.

- 제공자가 "그 세션 없다"고 말한 경우에만 그렇게 합니다. **할당량·인증 실패로 재개가 실패한 경우는 그대로 실패합니다** — 거기서 새로 시작하면 일시적인 장애 때문에 대화를 버리고, 진짜 원인을 잘 도는 것처럼 보이는 재시도 뒤에 숨기게 됩니다.
- 재시도는 **한 번뿐**입니다. 새 세션은 같은 이유로 실패할 수 없으므로, 또 실패하면 다른 문제이고 드러나야 합니다.
- 끊어진 연결은 지워지지 않고 `INVALID` 로 남습니다. 왜 대화가 끊겼는지가 다음 실행에도 남아 있어야 합니다.

```sh
goalforge sessions                  # 기억하고 있는 연결
goalforge sessions --drop active    # 이미 없어진 걸 아는 경우 직접 끊기
```

`ACTIVE` 는 **GoalForge 가 기억하는 값**입니다. 목록이 `ACTIVE` 라고 해서 제공자에 그 세션이 있다는 뜻은 아닙니다.

## 20. 워크트리가 사라졌을 때

GoalForge 는 작업마다 worktree 경로를 기억합니다. 그 경로도 **파일 시스템에 대한 주장**입니다. `git worktree prune`, 수동 삭제, 새로 클론, 디스크 초기화 — 그리고 PostgreSQL 큐를 공유하면 **다른 기계에서 만들어진 워크트리**를 이 기계의 워커가 집을 수도 있습니다.

기록된 경로는 **트리를 읽기 전에** 확인합니다. 아니면 이렇게 나옵니다:

```
fatal: cannot change to '/srv/myapp.goalforge-worktrees/W1': No such file or directory
```

저장소가 망가진 것처럼 읽히지만 실제 뜻은 다릅니다. 이제는 이렇게 말합니다:

```
recorded worktree is no longer present: /srv/myapp.goalforge-worktrees/W1 —
커밋된 작업은 브랜치 goalforge/PRJ-1-W1 에 그대로 남아 있습니다 —
git -C /srv/myapp worktree add ... 로 되살릴 수 있습니다.
커밋되지 않은 변경은 복구할 수 없습니다.
```

**무엇이 남았고 무엇이 사라졌는지**가 다음 행동을 정합니다. 커밋된 작업은 브랜치에 안전하고, 커밋되지 않은 변경은 복구할 수 없습니다 — 어떻게 표현해도 그렇습니다. 그래서 **조용히 다시 만들고 계속하지 않습니다.** 체크포인트가 기록한 변경이 없는 트리에서 이어 가는 것이 더 나쁩니다.

경로는 있는데 **다른 브랜치**가 올라가 있으면 거부합니다. 거기서 계속하면 남의 작업에 쓰게 됩니다.

## 21. 여러 기계에서 나눠 돌리기

기본값에서 작업 큐는 나머지 상태와 같은 SQLite 안에 있습니다. 그래서 `goalforge worker` 는
**자기 기계에서 넣은 작업만** 봅니다. 큐를 공유하려면 PostgreSQL 을 씁니다.

```sh
export GOALFORGE_POSTGRES_DSN='postgres://user:pass@host/goalforge?sslmode=require'
goalforge storage postgres migrate     # 최초 1회, 테이블 생성
goalforge serve                        # PostgreSQL 에 넣는다
goalforge worker                       # PostgreSQL 에서 꺼낸다
```

**배포 안의 모든 프로세스가 같은 값을 봐야 합니다.** `worker`, `serve`, `mcp`,
`continue --enqueue` 는 각각 시작할 때 큐를 한 번 정하고 어느 쪽을 쓰는지 알려 줍니다.

```
job queue: PostgreSQL (shared with other machines)
```

대시보드는 A 큐에 넣고 워커는 B 큐에서 꺼내는 배포는 **성공이라고 답하고 아무것도 실행하지
않는 버튼**을 갖게 됩니다. 같은 이유로, DSN 이 설정됐는데 연결되지 않으면 조용히 로컬 큐로
물러나지 않고 **시작을 거부합니다.**

PostgreSQL 이 조율하는 것은 **'누가 실행하는가'** 입니다. 목표·작업 항목·실행 기록·검증 증거는
여전히 각 기계의 SQLite 에 있습니다. 즉 공유 체크아웃을 보는 워커 풀에는 맞지만, 한 프로젝트의
이력을 여러 기계에 쪼개는 용도는 아직 아닙니다.

## 자주 묻는 것

**목표가 100% 인데 완료가 아니라고 나옵니다.**
작업 가중치와 필수 조건은 다른 지표입니다. `status` 의 `Criteria` 를 보세요. `[~]` 는 코드나 게이트가 바뀌어 재검증이 필요하다는 뜻입니다.

**게이트가 계속 실패하는데 자동 수정이 안 됩니다.**
실패가 환경·의존성·인증으로 분류됐을 가능성이 큽니다. 모델을 다시 돌려도 해결되지 않는 종류라 재시도하지 않습니다. `goalforge status` 의 `Needs you` 를 보세요.

**승인했는데 merge 가 거부됩니다.**
승인 이후 그 작업이 다시 실행되어 새 커밋이 생겼을 수 있습니다. 승인은 검토한 커밋에 고정되므로 새 변경은 다시 검토해야 합니다.

**샌드박스에서 게이트가 실패합니다.**
이미지에 프로젝트의 툴체인이 있는지, 네트워크가 필요한 작업이라면 `--network` 를 켰는지 확인하세요. 의심되면 `--mode none` 으로 되돌려 비교하면 됩니다.
